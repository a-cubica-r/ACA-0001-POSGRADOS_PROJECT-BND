# SC-05.1 · Identificación de valores hardcodeados (estados, tipos, categorías)

**Solicitud de cambio:** N.º 5 – Reemplazar valores hardcodeados por enum
**Sistema:** Backend / API del sistema de Posgrados
**Alcance de esta fase:** solo identificación. No se modificó código ni base de datos.
**Base de datos consultada:** `railway` (MCP `posgrados-db`, solo `SELECT`/`SHOW`).

## Resumen

Se revisó todo el backend: 666 archivos `.java` en `src/main` y unos 4.200 literales de texto, cruzados contra la BD.

- El cambio es seguro si cada enum guarda el **texto exacto de la BD** y la comparación sigue **ignorando mayúsculas**.
- Hay **6 puntos** donde la migración puede romper algo si se hace mal (sección 3).
- Hay **4 lugares** donde el literal actual ya **no coincide con los datos reales** (sección 4). Cambiar solo el literal por un enum los deja igual de rotos, y corregirlos cambia el comportamiento.

## 3. Dónde el cambio puede romper algo

1. **Valores con espacios.** `EN CURSO`, `PAZ Y SALVO`, `PENDIENTE DE CONFIRMACION` y `POR LEGALIZAR` no pueden ser el nombre de la constante. Cada enum necesita un campo `valor` con el texto exacto de la BD, y siempre hay que usar `getValor()`, **nunca `name()`**. Si se usa `name()` (`EN_CURSO`), la búsqueda devuelve `null` y falla en tiempo de ejecución.
2. **No usar `@Enumerated` en las entidades.** `estado.tipo` es una tabla compartida por `entidad` y se referencia por id (FK). Si se mapea la columna como enum, falla al leer valores con espacios o que no estén en el enum. Los enums deben quedarse en la lógica de negocio y las entidades seguir con `String`/FK.
3. **`@Query` con literales.** En [CohorteRepository.java:71](backend/api-base/src/main/java/ufps/edu/co/persistence/repositories/CohorteRepository.java:71), [CohorteRepository.java:79](backend/api-base/src/main/java/ufps/edu/co/persistence/repositories/CohorteRepository.java:79) (consulta nativa) y [AdministrativoRepository.java:62](backend/api-base/src/main/java/ufps/edu/co/persistence/repositories/AdministrativoRepository.java:62), Java no permite usar `Enum.X.getValor()` dentro de una anotación (no es una constante de compilación). Hay que convertirlos en parámetros (`:entidad`, `:tipo`) y pasar el valor del enum desde el servicio.
4. **El `switch` de pasos del proceso.** [AspiranteCoreService.java:548](backend/api-core/src/main/java/ufps/edu/co/services/core/crud/AspiranteCoreService.java:548) usa `""` cuando no hay estado y cae en `default`, y lo mismo pasa con estados como CANCELADO o EN PROCESO. Al cambiar a enum, `fromValor()` debe devolver `Optional` o un valor por defecto. Un `switch` sobre un enum `null` lanza `NullPointerException`.
5. **Contrato con el frontend.** Las salidas como "completado", "en progreso", "pendiente", "validados" y el `estado` de los documentos se envían tal cual. El enum debe serializar exactamente el mismo texto en minúsculas.
6. **Entradas de la API.** `DocumentoInput.estado`, `PagoEstadoInput.estado` y `ProgramaInput.tiporegistroTipo` reciben texto libre. Si se cambian a tipo enum, Jackson rechazará minúsculas o valores con espacios, y no hay `ACCEPT_CASE_INSENSITIVE_ENUMS` configurado en `JacksonConfig`. Recomendación: dejarlos como `String` y convertirlos dentro del servicio.

### Comportamiento que hay que conservar

- Seguir comparando sin distinguir mayúsculas (`equalsIgnoreCase` + `trim`). `PagoCoreService` además normaliza con `toUpperCase(Locale.ROOT)`.
- Los repositorios sin `IgnoreCase` (`RolRepository.findByNombre`, `EstadodocumentoRepository.findByEstado`, `TiporegistroRepository.findByTipo`, `SedeRepository.findFirstByNombre`) solo funcionan hoy gracias a la collation `_ai_ci`. El enum de `Rol` debe guardar el nombre real de la BD (`Aspirante`), no solo `ASPIRANTE`.
- Las búsquedas dobles (`"aspirante"` y luego `"ASPIRANTE"`, `"pago"` y luego `"PAGO"`, etc.) sobran, porque `EstadoRepository.findByTipoIgnoreCaseAndEntidadIgnoreCase` ya ignora mayúsculas. Se pueden quitar sin cambiar el comportamiento.
- `RoleNameNormalizer` convierte los nombres de la BD en los códigos que espera `SecurityConfig` (`Director de Programa` → `DIRECTOR_DE_PROGRAMA`). El enum `Rol` debe mantener esos códigos.

## 5. Solución propuesta

### 5.1 Dónde ubicar los enums

En **`api-base`** (por ejemplo `backend/api-base/src/main/java/ufps/edu/co/enums/`). Es el módulo del que dependen todos los demás:

| Módulo            | Depende de                       |
| ----------------- | -------------------------------- |
| api-auth          | api-base                         |
| api-core          | api-base, mail-module, api-wompi |
| api-rest          | api-core, api-auth, mail-module  |
| api-wompi         | api-base                         |
| mail-module       | api-base                         |
| platform/security | api-auth (→ api-base)            |

Así los repositorios, servicios, casos de uso y `SecurityConfig` pueden usarlos.

### 5.2 Forma de cada enum

Se sigue el patrón que ya usan los `*ErrorCode` (`@Getter @AllArgsConstructor`):

```java
@Getter
@AllArgsConstructor
public enum EstadoAspirante {
    NO_CONFIRMADO("NO CONFIRMADO"),
    INSCRITO("INSCRITO"),
    PAZ_Y_SALVO("PAZ Y SALVO"),
    VALIDADO_POR_CALIFICAR("VALIDADO_POR_CALIFICAR"),
    // ...
    ;

    public static final EntidadEstado ENTIDAD = EntidadEstado.ASPIRANTE;

    private final String valor;

    public boolean matches(String tipo) {
        return tipo != null && valor.equalsIgnoreCase(tipo.trim());
    }

    public static Optional<EstadoAspirante> fromValor(String valor) {
        if (valor == null) return Optional.empty();
        return Arrays.stream(values()).filter(e -> e.matches(valor)).findFirst();
    }
}
```

Para `Rol`, guardar dos campos:

- `nombreBd`: "Director de Programa", para las búsquedas en la BD.
- `codigo`: "DIRECTOR_DE_PROGRAMA", lo que produce `RoleNameNormalizer` y usa `SecurityConfig`.

### 5.3 Métodos de ayuda en los servicios

Para no repetir la entidad en cada llamada, agregar sobrecargas como estas:

- `EstadoService.findByTipoAndEntidad(EstadoAspirante.ADMITIDO)`, que use internamente `getValor()` y `ENTIDAD`.
- `EstadodocumentoService.findByEstado(EstadoDocumento)`.
- `RolService.findByNombre(Rol)`.

Se dejan las firmas actuales con `String` para no romper otros llamados ni los tests.

### 5.4 Reemplazar uso por uso (en el orden de la sección 2)

| Antes                                  | Después                                                            |
| -------------------------------------- | ------------------------------------------------------------------ |
| `"X".equalsIgnoreCase(t)`              | `Enum.X.matches(t)`                                                |
| `findByTipoAndEntidad("X", "entidad")` | `findByTipoAndEntidad(Enum.X)`                                     |
| `List.of("A", "B")`                    | `Stream.of(Enum.A, Enum.B).map(Enum::getValor).toList()`           |
| `switch (estado) { case "X" -> ... }`  | `fromValor(estado).orElse(null)` con un caso por defecto explícito |
| `@Query("... = 'ABIERTA'")`            | `@Query("... = :tipo")` + `@Param("tipo")`                         |

### 5.5 Qué no cambiar

Las entidades JPA, los DTO y records de entrada/salida, ni los datos de la BD. Con eso el comportamiento se mantiene.

### 5.6 Casos de la sección 4

Documentarlos y decidir aparte (con el equipo o con otra solicitud de cambio) si se corrigen, porque corregirlos cambia el comportamiento actual.
